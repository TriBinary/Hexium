# Technical architecture

The music's playback position is the only clock. Minecraft's 20 TPS tick (50 ms) is never used for anything that is timed or drawn in gameplay. All game rules live in a pure-Kotlin `core` module that the mod and the server share. That lets the server re-judge replays with exactly the same code.

## Toolchain

Minecraft 26.3 is unobfuscated, so no mappings are needed. The project uses Gradle 9.8.2, Fabric Loom 1.19, Fabric Loader 0.20.1, Fabric API 0.165.0+26.3, Kotlin 2.4.21, Fabric Language Kotlin 1.14.2 and kotlinx-serialization-json 1.11.0, on Java 25. `gradle.properties` and the Gradle wrapper are the source of truth for versions; update this line when they change. Hexium is written in Kotlin with Gradle Kotlin DSL build scripts. The mod depends on Fabric Language Kotlin, which players install alongside Fabric API. Mixins stay in Java: each one is a few lines that call into Kotlin.

`core` reads and writes chart JSON with kotlinx-serialization-json's tree API (`JsonElement`), without the compiler plugin or annotations on the model, so the parser can report every error in a file with its path. The mod doesn't bundle the library: Fabric Language Kotlin already ships it, so `kotlinx_serialization_version` in `gradle.properties` must stay on the version Fabric Language Kotlin bundles. When bumping Fabric Language Kotlin, also raise its minimum version in `fabric.mod.json`.

## Gradle modules

| Module | Depends on | Holds |
| --- | --- | --- |
| `core` | only kotlinx-serialization-json (plain Kotlin/JVM, Java 25) | Chart model, parser, validator, timing map (BPM changes → ms), judge engine, scoring, replay format |
| `mod` | `core`, Fabric API, Fabric Language Kotlin | Menu, session, stage loading, audio clock, input capture, rendering, HUD, screens, editor, network client |
| `server` | `core` | Backend API, auth, chart storage, leaderboards, replay verifier |
| `tools` | `core` | CLI: chart lint, replay re-judge, replay dump (used by CI and developers) |

Only `core` knows the rules. The mod, the server and the `tools` CLI all depend on it.

## Session gating ("normal worlds are untouched")

- The title screen gets one extra button that opens the mod's menu. That menu is the only place a `HexiumSession` is ever created.
- Every mixin and event hook starts with `if (!HexiumSession.active()) return;`, except the title screen button, which only adds that button. Joining a normal world or server means no session, so vanilla behaviour stays as it was.
- The stage is a flat black floor with a small platform for the player, made in code (`StageWorld`) and created fresh for each session in the mod's own folder, `.minecraft/hexium/stages/`, not `saves/`, so it never shows up in the vanilla world list. Making it in code means a Minecraft update can't ask to upgrade it. Chart-authored stages may bring template worlds in Milestone 8. It runs on the integrated server, with its rules frozen once the player joins: no daylight cycle, mobs, random ticks or weather.
- The player is in adventure mode on Peaceful, placed on the stand spot on top of the platform. Gameplay never depends on the server; the world is just scenery.
- While a session is active, mixins hold the player still (`KeyboardInput`), stop every key that method handles (`Minecraft.handleKeybinds`: attack, items, hotbar, inventory, chat, F1, F5 and so on) and hotbar scrolling, keep vanilla's tutorial from starting, since it would end itself for good outside survival, and replace vanilla's pause menu. The camera turns with the mouse, but stops 1.54 blocks past the sky screen's edges (`Aim`, with the maths in `ScreenPlane` in `core`), so the player can't spin away from the stage. Vanilla's HUD stays apart from the hunger bar, which is hidden, and Hexium draws combo, judgement and score over it. While no screen is open, vanilla doesn't see lane keys at all, so the play loop tells it there was input, or it would lower the frame rate. A player arriving in third person or with the HUD hidden gets the normal view, and their own comes back afterwards.
- A session ends when the connection closes, and also whenever the title screen or the Hexium menu opens, so a failed load can't leave one running.

## Audio and clock

- Songs are not played through Minecraft's sound manager. The mod decodes OGG with stb_vorbis (bundled with LWJGL) on a background thread and streams it into its own OpenAL source on the game's existing OpenAL context (`SongStream`). Minecraft destroys that context when the audio device changes or sounds reload, so a mixin stops the stream first, and it rebuilds its source on the new one at the clock's current time. The song is silent while Minecraft's loading screen covers the game.
- Song position comes from `AL_SEC_OFFSET_LATENCY_SOFT` (the OpenAL Soft latency extension), or `AL_SAMPLE_OFFSET` if it isn't there. This raw value updates in steps, so the clock runs on SDL's tick counter, the clock input events are stamped with, and is gently pulled toward the audio position. It only jumps if the audio is over 100 ms away, or for the first position after a lead-in, and never runs backwards: it holds still until the music catches up. The logic is `SongClock` in `core`, which has no time source of its own, so it can be tested. `AudioClock` in `mod` feeds it.
- Vanilla music is held for the length of a session.
- Draw time = song time − visual offset (A). Judgement time = input song time − judgement offset (B).

## Input timing

- Minecraft 26.3 uses SDL3, not GLFW. Read lane keys in `SDLEventHandler` (`LaneInput`), since it hands keys on to the keyboard handler later in the frame, and the left and right mouse buttons there too (`SkyInput`). A click that grabs the mouse back after the window lost focus still reaches vanilla, so it can, and a release always goes wherever its press went, so vanilla never sees half a click. Keys are physical positions, so the left hand sits the same on any layout. Each SDL event carries a `timestamp` from SDL's tick counter (`SDL_GetTicksNS`), the same clock the song clock runs on, so convert that to song time with the clock's mapping.
- Events are polled once per frame, so without a real timestamp from the OS the error is at most one frame. The debug overlay's `key stamp age` hints at whether stamps are real: at a low frame rate they should spread from about 0 up to a frame. Tell players to run uncapped or at 240+ FPS during play (about 4 ms of error). Keep rendering fast so this holds.
- Every frame, record an aim sample: where the camera's look ray from the eye meets the screen plane (`ScreenPlane`), as normalised screen coordinates. Slides and flicks are judged from these samples. Flicks test the line between two samples, so fast swipes at low FPS still register.
- Events go into fixed rings. The play loop (`PlaySession`) reads the clock at the start of every frame, before anything reads the time. Vanilla turns the camera with the mouse later in the frame (`MouseHandler.handleAccumulatedMovement`), so only then does the play loop keep the camera within its limit, drain keys and buttons oldest first, and send the frame's aim sample, before anything is drawn. So a sample is where the camera really pointed that frame, and a click is placed there too: a click's own position within the frame isn't known. A play has a 3-second lead-in with the clock running before the music, and stays open 2 seconds after the last note.
- Pausing stops the song and clock together. Resuming goes back 3 seconds, or to before the song if that's where it lands, and plays on from there under a 3-2-1 countdown. `PlayInput` in `core` holds the rule: nothing is judged or recorded until the song is back at the pause point, and any lane key or sky button that changed in between is pressed or released at exactly that time. The crosshair is recorded where it last was at the pause point, and again where it is on its way to the frame that reopens judging, at that same time, so moving the mouse while paused isn't a swipe ([REPLAY_FORMAT.md](REPLAY_FORMAT.md)). Keys are read while the pause screen is open too, so this knows which are really down. Notes already judged stay hidden during the countdown, and so does the part of a hold already played.
- A finished play opens `ResultsScreen` and saves its replay. Retry, on that screen and the pause screen, loads a new `PlaySession` for the same chart and keeps the stage. Leaving or retrying part way through saves nothing.
- A key usually arrives after a later frame has read the time: on a Mac at 170 FPS, most stamps were already older than the last frame. So `PlayInput` holds aim samples and the judge's clock 50 ms behind the song. A key is judged at once at its own stamp, after the samples older than it, so hits show straight away and only Misses, ticks and, from Milestone 3, slide and flick results show up to 50 ms later. Sky buttons go through `PlayInput` the same way, with the crosshair at the click, never straight to `ReplayRecorder`, or they would land out of order with the held-back samples. A key or button older than the judge's current time moves up to it and counts as a `late key`: that takes a stamp more than 50 ms behind the previous frame, or one older than a newer key or the pause point. Calibration reads the same stamps, so offset B applies to the times it was measured on.
- Events go through the judge every frame. Every input event and aim sample is also appended to the replay: the mod sends all input through `PlayInput`, then `ReplayRecorder`, which records it and passes it to the judge ([REPLAY_FORMAT.md](REPLAY_FORMAT.md)).

## Calibration

`CalibrationScreen` suggests offsets A and B on a plain screen, without the stage. It holds a session and plays the bundled click track on the same `AudioClock`, and `LaneInput` reads taps with the same SDL timestamps as a play, so it measures what a play would see. For the second step the song keeps running in silence, so the clock is the same. The maths is in `Calibration` in `core`. Taps from the first half second are ignored while the clock settles, as are the first two after that while the player finds the beat. Step one won't start with the music volume at 0, since steady taps to nothing would pass, and taps that slide off the beat or scatter are sent back. Vanilla holds this screen to 60 FPS, so against a 240 FPS play the notes it shows are about 6 ms older: this estimates A a little low, so taps may judge a few ms early.

## Rendering

- `TrackRenderer` draws through Fabric's `LevelRenderEvents.COLLECT_SUBMITS` and `submitCustomGeometry`, never raw OpenGL, since 26.3 can run on Vulkan. Only notes inside the visible time window are drawn: `GroundTrack` in `core` holds them in time order and finds where to start, and every position is worked out fresh from draw time, so a note can't drift from the clock. A note's distance up the lane is `(note time − draw time) × note speed`, and speed never changes when it arrives.
- For now the render type doesn't write depth and, with classic transparency, sorts quads by their centres, so a long floor quad could paint over a note behind its middle. So the floor, hold bodies and notes are each submitted in their own order, which are drawn in turn, and a note only emits the faces the camera can see. Improved transparency (the Fabulous preset) draws these on a different path; the game test takes a screenshot of it to check by eye. A note goes once the judge has its head, and a hold's body stops at the line, shortening as it plays. Vertices are relative to the camera on an untransformed pose, as vanilla's entities are, so no matrix is applied per vertex.
- Notes are plain coloured shapes until Milestone 5 brings block models (note block styles per type). Ground notes are cuboids and hold bodies stretched quads. `SkyRenderer` draws after the ground, in orders of its own: the sky notes, then the screen as a faint pane with a frame in front of them, so they show through it, then the rings on the screen. `SkyTrack` in `core` holds sky taps, slides and flicks in time order the way `GroundTrack` holds ground notes, with each note's hit radius from `JudgementConfig` and a slide's position at any time from the same `SlidePath` the judge uses. A sky note flies down the depth axis at the note speed as a flat octagon facing the player, just covering its hit circle: taps orange (L) or blue (R), flicks magenta. A slide is a trail of small beads on a fixed time grid down its path, with a ring where it crosses the screen now, white while its button is down. A tap or flick within 24 blocks also shows a faint ring on the screen where it will land, and a late one waits on the screen until it's judged or its window passes. During the rewind after a pause, the part of a slide before the pause point isn't drawn, as with hold bodies.
- Note speed and visual offset A live in `PlaySettings`, changed from the pause screen, and A also by calibration. They reach only `TrackRenderer` and `SkyRenderer`, so the judge and replays never see them. Offset B is read when a play starts and goes in its replay.
- The comfort settings live in `PlaySettings` too and act only on the camera (`Comfort`): play sensitivity scales the turn vanilla's `MouseHandler.turnPlayer` hands the player, play FOV replaces `Camera.calculateFov`'s result, and view assist eases the camera toward the rest view in the play loop, by song time, before the camera limit, when no sky note is due within 1.5 seconds or can still be judged. Outside a play they do nothing, so menus and normal worlds feel the same.
- Hit effects are client-only particles and a short sound, with a hit-sound volume setting.
- Performance budget: 240 FPS with 300 notes on screen on a mid-range GPU. F6 during a play shows a debug overlay with the song position, clock drift, frame time, the offsets, and input-to-judgement delay as `key stamp age`: how old a key's SDL timestamp is at the start of the frame that judges it (minimum, average, maximum). Judged times come from the stamp unless it's older than the judge's current time, which `late keys` counts, and it can't see the keyboard's own delay. It rebuilds its text every quarter second. It stays on across plays until the game closes, and F3+F6 still reaches vanilla.

## Local data

`.minecraft/hexium/` holds `charts/` (one folder per chart package; the mod also bundles a test pack in `hexium_packs/`), `replays/` (one `<chart>-<difficulty>-<date>-<time>.hexreplay` per finished play, never cleaned up for now), `scores.json` (best scores per chart) and `settings.json` (note speed, offsets A and B, and the comfort settings: play mouse sensitivity, play FOV and view assist, read by `PlayerSettings` in `core`, which can always read something: a broken file or field gives the default, and it doesn't check `formatVersion`, so a later version must keep these fields' meaning). That's enough for v1. A real database only lives on the server.
